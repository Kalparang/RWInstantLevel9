# 업데이트와 구조 변경 가이드

현재 구현은 [ARCHITECTURE.md](ARCHITECTURE.md)의 특정 게임 빌드에 맞춘 네이티브 훅입니다. 새 버전 대응 시 실행 파일 SHA-256만 바꾸어 활성화하면 안 됩니다. 명령어가 비슷해도 레지스터 용도, 자료형, 객체 배치 또는 저장 흐름이 달라질 수 있습니다.

빌드 및 자동 검증 명령은 [DEVELOPMENT.md](DEVELOPMENT.md)를 참고하세요. 이 문서는 변경할 지점과 검증 기준을 설명합니다.

## 게임 업데이트 대응

1. **기준을 고정합니다.** 새 실행 파일의 버전, Steam build와 SHA-256을 기록합니다. 게임을 종료하고 전체 `_Save`를 별도 위치에 백업한 뒤 원본과 백업 파일들의 SHA-256이 일치하는지 확인합니다. 개발용 세이브와 분석 결과는 공개 저장소에 추가하지 않습니다.
2. **영구 경험치 지급 흐름을 다시 찾습니다.** 기존 RVA는 탐색의 기준점으로 사용합니다. 실제 플레이한 영웅을 선택하고 판 종료 XP를 합산한 뒤 프로필과 결과 객체를 갱신하는 경로인지 확인합니다. 전투 중 경험치, 계정 단위 경험치 또는 UI 표시만 바꾸는 경로와 혼동하지 않도록 데이터 흐름을 추적합니다.
3. **프로필 표현과 설정을 확인합니다.** 프로필 타입, vtable RVA, 성장도 필드의 위치/자료형, 표시 레벨 계산, XP 임계값 배열, 최대 레벨 필드를 재검증합니다. 저장된 값이 계속 정규화된 성장도인지 확인합니다. 클래스 레지스트리 인덱스는 고정값으로 가정하지 않습니다. 이 게임의 이전 도구와 현재 빌드 사이에서도 영웅 클래스 인덱스가 달라진 사례가 있습니다.
4. **훅 ABI를 다시 작성합니다.** before/after 지점의 레지스터 역할, 스택 정렬, 살아 있는 플래그와 SIMD 상태, 원본 명령어 길이 및 상대 주소 명령어를 확인합니다. MinHook이 옮기는 명령어를 트램펄린에서 실행해도 원래 흐름이 유지되는지 검토합니다.
5. **관련 상수를 함께 갱신합니다.** [src/mod.cpp](../src/mod.cpp)의 `ExpectedHash`, `BeforeRva`, `AfterRva`, `ProfileVtableRva`, `BeforeBytes`, `AfterBytes`, 객체 필드 오프셋을 확인합니다. 레지스터 계약이 달라졌으면 [src/mastery_hook.asm](../src/mastery_hook.asm)도 변경합니다. 버전 및 `READY` 로그의 설명 문자열도 실제 지원 범위와 일치시킵니다.
6. **독립 계산 정책을 검토합니다.** XP 자료형이나 임계값 의미가 달라지면 [src/mastery_policy.h](../src/mastery_policy.h)의 자료형, 범위 검사, 반올림 허용치와 목표량 계산을 수정합니다. 최대 레벨이 9가 아니면 현재 코드는 원래 지급량을 유지하도록 되어 있습니다. 이를 지원하려면 제품 동작과 저장 형식을 먼저 정의해야 합니다.
7. **자동 검사 후 실제 지급을 검증합니다.** 아래 절차를 순서대로 수행합니다. 실행 파일 검증을 통과해 `READY`가 나왔다는 사실과 실제 경험치 지급/저장 성공을 별도로 기록합니다.

여러 빌드를 지원하도록 바꿀 때는 해시별 RVA·시그니처·필드 배치·ABI 계약을 함께 관리하세요. 단순히 하나의 해시 검사를 제거하거나 모든 버전에 같은 오프셋을 적용하면 지원 여부를 판단할 수 없습니다. 서명 검색을 도입하더라도 단일 바이트 패턴 일치만으로 구조 호환성을 인정하지 않아야 합니다.

## 자동 검증을 갱신할 때

[tests/native_tests.cpp](../tests/native_tests.cpp)는 순수 정책과 실제 x64 detour/trampoline 실행을 검사합니다. 단순히 C++ 콜백을 직접 호출하는 테스트로 대체하면 함수 중간 ABI 문제를 놓칠 수 있습니다. 실제 훅 지점의 명령어가 바뀌면 [tests/native_fixture.asm](../tests/native_fixture.asm)의 해당 명령어와 주변 레지스터 계약도 함께 갱신합니다.

최소한 다음 의미 있는 경우를 포함합니다.

- 9레벨 미만에서 양수 지급을 받으면 정확히 남은 XP로 바뀝니다.
- 지급량 0과 이미 9레벨인 경우 원래 지급량을 유지합니다.
- 음수/NaN/무한대 성장도, 예상과 다른 최대 레벨, 증가하지 않는 곡선, 누적 XP 불일치를 거부합니다.
- 16비트 경계와 큰 지급량에서 넘침이 생기지 않습니다.
- 콜백이 휘발성 레지스터를 덮어써도 원래 명령어의 최종 레지스터/플래그 결과가 유지됩니다.
- before 훅이 프로필의 성장도 필드를 직접 변경하지 않으며 after 관찰 훅이 원래 실행을 유지합니다.

[tests/proxy_smoke.cpp](../tests/proxy_smoke.cpp)는 현재 92개 export의 존재와 16개 스레드의 지연 초기화 및 로컬 WinHTTP 세션 열기/닫기를 검사합니다. 네트워크 요청은 보내지 않습니다. 이는 모든 export를 실제 인자로 호출하거나 모든 Windows 버전에서 검증했다는 뜻은 아닙니다. export 목록 또는 전달 어셈블리를 변경했다면 이름·ordinal·호출 규약과 새 지원 Windows 환경을 별도로 확인하세요.

현재 네이티브 fixture는 프로덕션 `mod.cpp`의 전체 초기화 루틴을 실행하지 않습니다. 따라서 자동 검사가 통과해도 실행 파일 해시 검사, 실제 게임 객체 수명, 후킹 위치 및 게임 저장 처리는 실제 런타임에서 확인해야 합니다.

## 실제 게임에서 확인할 순서

1. 게임을 종료한 상태에서 전체 세이브 백업을 검증하고 빌드한 DLL을 설치합니다. 기존에 같은 이름의 DLL이 있으면 설치 대상과 소유자를 확인합니다.
2. 게임을 실행하여 로그의 `READY`를 확인합니다. 아직 경험치를 지급받지 않은 상태에서 세이브 성장도가 바뀌지 않았는지 확인합니다.
3. 영구 9레벨 미만인 영웅으로 플레이하여 양수의 영구 경험치를 받습니다. `AWARD`의 보정량이 목표 누적 XP까지 남은 양인지, `COMMIT`의 반영된 성장도가 표시 9레벨인지 확인합니다.
4. 결과 화면의 레벨, 경험치 요약, 해금/보상 표시를 확인합니다. 훅이 통과한 사실만으로 UI나 모든 해금 처리가 올바르다고 판단하지 않습니다.
5. 게임의 정상 저장이 끝난 뒤 프로필을 읽기 전용으로 비교합니다. 영웅 성장도는 해당 영웅에서만 의도대로 바뀌었는지 확인하고 저장 형식이 지원되면 무결성도 검사합니다. 플레이 통계 등 정상적인 게임 진행 변경과 구분해 평가합니다.
6. 게임을 완전히 종료하고 다시 실행하여 9레벨과 필요한 해금이 유지되는지 확인합니다.
7. 가능하면 경험치 0과 이미 9레벨인 영웅의 실행 사례를 확인합니다. 새로운 게임 모드나 협동 플레이를 지원한다고 표시하려면 그 경로에서도 별도로 검증합니다.

비활성화 표식과 제거 절차는 [README.md](../README.md)에 있습니다. 표식을 적용하려면 게임을 종료한 뒤 다음 실행 전에 생성하세요. 모드 제거는 이미 저장된 영구 레벨을 되돌리지 않습니다. 되돌림이 필요하면 게임이 종료된 상태에서 검증된 전체 세이브 백업을 사용하고 클라우드 저장 충돌 여부를 확인합니다.

## 구조를 바꿀 때 유지할 경계

- **계산과 메모리 접근:** 정책은 가능한 한 순수 함수로 두고 게임 메모리 읽기와 예외 처리는 `mod.cpp`에 둡니다. 이를 통해 합성 입력으로 경계값을 검증할 수 있습니다.
- **지급과 반영:** before 훅은 지급량만 조정하고 원래 엔진의 반영·레벨 상승·저장 흐름을 통과시킵니다. 관찰 훅에 상태 변경을 추가하려면 검증 범위도 다시 정의해야 합니다.
- **동시성:** 현재 관찰 연결은 단일 pending 슬롯입니다. 지급 흐름이 병렬 또는 재진입 가능해지면 스레드별 또는 호출별 연결과 객체 수명을 함께 설계합니다.
- **프록시와 게임 훅:** WinHTTP 전달은 비게임 테스트 호스트에서도 동작해야 합니다. 게임 훅 초기화나 네트워크 요청을 프록시 해석 함수에 섞지 않습니다.
- **실행 중 수명:** 현재 모드는 프로세스 종료까지 로드되는 방식입니다. 실행 중 DLL 언로드를 지원하지 않으며 `DllMain`의 종료 경로에서 후킹 해제 작업을 하지 않습니다. 재로딩 기능을 추가하려면 콜백 실행 중 해제와 스레드 정지 문제를 별도로 해결해야 합니다.

## 현재 검증 범위

기존 `1.0.0` 빌드에 대한 확인 내역입니다. 이후 코드나 게임 빌드가 바뀌면 새 검증 결과로 갱신하세요.

| 구분 | 확인한 범위 |
| --- | --- |
| 빌드 | Release MSVC x64 빌드 성공 |
| WinHTTP | CTest `proxy_forwarding` 통과: 92개 export, 16개 스레드의 로컬 세션 전달 |
| 네이티브 훅 | CTest `mastery_native_hooks` 통과: 11,042개 검사, 1,000회 before detour/trampoline 실행 및 after 관찰 훅 |
| 공개 소스 재빌드 | 포함된 파일만으로 Release 빌드 및 CTest 2개 통과, 합성 프로필 Python 테스트 16개 통과 |
| 실제 지급 | 단독 플레이의 양수 영구 XP 지급 후 엔진이 표시 9레벨을 반영 |
| 저장 | 실제 프로필에 저장된 9레벨과 저장 데이터 무결성을 읽기 전용으로 확인 |
| 실행 복귀 | 판 종료 후 로비 복귀 확인 |

재실행 후 유지, 결과 화면의 정확한 XP 표시, 모든 보상/해금, 협동 플레이 및 모든 게임 모드의 경로는 별도 검증 전입니다. 경험치 0과 이미 9레벨인 경우는 자동 네이티브 검사 범위에 포함되지만 각각의 실제 플레이 검증은 별도입니다.

공개 자료에는 개인 세이브, 영웅별 실제 진행도, 프로필 해시, 계정 식별자, 사용자 절대 경로, 로컬 로그 또는 메모리 덤프를 넣지 않습니다. 문제 재현 예시는 합성 값으로 작성하고 실제 로그를 공유해야 한다면 필요한 필드만 추려 익명화합니다. 게임 실행 파일과 리소스는 저장소에 포함하지 않습니다.
